Agentic SDLC · build & rollout guide

SDLC Pipeline Flow

How a vague requirements file becomes reviewed Jira stories, and how a story becomes a reviewed merge request. This page shows the flow, then each stage with its config, inputs and outputs, then how config, skills, packaging and multi-repo features fit together. The running example adds rate limiting to a todo-api service.

Flow Phase contract Stage reference Config layers Skills & instructions Packaging Commands Multi-repo Human gates Giving feedback Pause & resume Build order Rollout
Script (Phase 1, no LLM) LLM skill (Phase 2 sandbox) Human External system Escalation Forward flow Feedback loop (with its limit)

Phase 1 ↔ Phase 2 contract

Every LLM stage runs the same way. Phase 1 writes /io/in/task.json plus the input files and starts a fresh sandbox. The sandbox writes /io/out/result.json plus artifacts and exits. Phase 1 checks the result against its schema before doing anything with it.

Inside the sandbox: Claude Code, not the raw API

Every LLM call is claude -p running in the Phase 2 container, so skills, CLAUDE.md, subagents and commands are picked up the way Claude Code normally does it. The LLM gateway is only the endpoint Claude Code talks to.

Container layout 
/etc/claude-code/managed-settings.json   org policy
/etc/claude-code/managed-mcp.json        no servers

$CLAUDE_CONFIG_DIR = /run/claude   (run volume)
  CLAUDE.md                org instructions
  skills/<name>/           org skill library
  agents/  commands/       org extras
  projects/-workspace/     sessions → --resume

/opt/sdlc/packs/<pack>/.claude/skills/   --add-dir

/workspace/   (cwd = the repo)
  CLAUDE.md  .claude/skills  .claude/agents
  .claude/commands  .sdlc/  openspec/
  (.claude/settings*.json removed)

/io/in/   task.json  contract.md  inputs/
/io/out/  result.json  questions.json  artifacts/
How the worker calls it · entrypoint.py 
claude -p "/grill-with-docs $(cat /io/in/prompt.md)" \
  --model "$MODEL" \
  --append-system-prompt-file /io/in/contract.md \
  --add-dir /opt/sdlc/packs/kotlin-service \
  --permission-mode dontAsk \
  --max-turns "$MAX_TURNS" \
  --output-format json \
  ${SESSION_ID:+--resume "$SESSION_ID"} \
  > /io/out/claude.json

Anything a team adds to .claude/skills, .claude/agents, .claude/commands or CLAUDE.md is used on the next run. CLAUDE_CONFIG_DIR lives on the run volume, so grill sessions resume across short-lived containers. To confirm in the P2 spike: the managed-settings path on Linux, that resuming works across containers, and that skills load from --add-dir.

Stage reference

A1

Grill + answer questions

LLMhumanPhase 2 · entry skill grill-with-docs → grilling + domain-modeling
Takes
  • Redacted requirements and context, intake.json
  • The repo, read-only (grilling explores the code instead of asking, where it can), existing openspec/specs, CONTEXT.md
  • Earlier answers, via the resumed session
Produces
  • needs_input + questions.json, each question with a suggested default
  • A clarity checklist each round (clear, assumed or open, with evidence)
  • When the checklist is clear: ok + qa-log.md
  • Updated CONTEXT.md glossary and docs/adr/*, from domain-modeling. These go into the spec MR
Config 
stages:
  grill: { entry_skill: grill-with-docs }
llm:
  stages:
    grill: { model: claude-sonnet-5-5, max_turns: 6 }
grill:
  style: { cli: one_at_a_time, file: batch }
  mode: until_clear       # bounded | until_clear
  max_rounds: null        # optional cap
  questions_per_round: null
  readiness_threshold: null
  soft_warn_rounds: 6     # notify only
  stop_when: [checklist_clear,
              no_new_questions, human_done]
budgets:
  per_stage_usd: { grill: 1.50 }  # always on
Output, round 1 · questions.json 
{
  "status": "needs_input",
  "open": ["acceptance_criteria",
           "error_behaviour", "storage"],
  "questions": [
    { "id": "q1",
      "text": "What limit per client?",
      "default": "100 req/min per API key" },
    { "id": "q2",
      "text": "Response when limited?",
      "default": "429 with Retry-After" },
    { "id": "q3",
      "text": "Where is the counter stored?",
      "default": "Existing Redis" }
  ]
}
Human answers → final output · qa-log.md

#   1 item assumed)

Readiness · clarity checklist, checked by a script 
{
  "ready": true,
  "checklist": [
    { "item": "problem_and_goal",
      "status": "clear", "evidence": ["req:L3", "q1"] },
    { "item": "error_behaviour",
      "status": "clear", "evidence": ["q2"] },
    { "item": "nfr_performance",
      "status": "assumed", "evidence": ["q3:default"] },
    { "item": "acceptance_criteria",
      "status": "clear", "evidence": ["q1", "q2"] }
  ]
}
// script: no "open" items, every item cites
// evidence, "assumed" items copied into
// proposal.md as open assumptions

Loops back to itself with the answers. By default (until_clear) there's no round cap. It moves on to A2 when a script confirms no checklist item is open, when a round adds no new questions, or when the user types done. The grill budget is the only hard stop, and hitting it escalates. bounded mode adds a round cap and a readiness threshold.

A4

Publish

scriptPhase 1 · jira_publish.py, confluence_publish.py
Takes
  • Change folders, merged on main
Produces
  • One Jira story per change. Scenarios become the acceptance criteria, tasks.md becomes a checklist, and the change id becomes a label.
  • A Confluence page rendered from proposal.md and design.md
  • published.json, which makes reruns safe (no duplicates)
Config

  confluence: { space: ENG, parent_page_id: "12345" }
openspec:
  change_to_jira: story     # story | epic
  confluence_mirror: true
publish:
  dry_run: false
  labels: [ai-pipeline]

Config layers

The stage graph is Python code. Everything you'd want to tune is YAML in three layers, merged in this order. A lower layer can make a guardrail stricter but can't loosen a key the org has locked.

1 · Org defaults · config/org.yaml

  gateway_url: http://llm-gateway:4000
  allowed_models: [claude-haiku-4-5-20251001,
                   claude-sonnet-5-5,
                   claude-opus-5-5]
  stages:
    grill:     { model: claude-sonnet-5-5 }
    propose:   { model: claude-sonnet-5-5 }
    implement: { model: claude-sonnet-5-5 }
    review:    { model: claude-opus-5-5 }
budgets:
  max_per_run_usd: 10.00     # locked ceiling
  per_run_usd: 5.00
gates:
  spec_review: { value: true, locked: true }
  mr_review:   { value: true, locked: true }
guardrails:
  forbidden_paths:           # locked: append-only

Skills & instructions

Four layers, each from a different source. All of them end up in the sandbox where Claude Code loads them: the user level ~/.claude/ for pipeline-wide layers, and the project level /workspace for the repo. Prompts from any layer can add rules. Only the enforcement layer on the right can block anything.

Packaging: a CLI, not a plugin

sdlc is a command-line tool, installed like openspec or gh. It's a thin front end: in local mode it starts the stack on the laptop, and in shared mode it calls the central API. People use the same commands in both. A Claude Code plugin can come later, as another front end that calls the CLI, but never as the engine. A plugin would run with the developer's own credentials and network, which undoes the sandbox.

Rolling it out to other teams

Grow it in three stages. Each stage moves the credentials and the cost further away from individual laptops and into the hands of an owning team.

STAGE 1 · PILOT

Local CLI

  • You and one pilot team, one repo
  • docker compose up on each laptop
  • Developers bring a .env with bot tokens for the pilot project

Move on after 2–4 weeks of reliable runs on real tickets.

STAGE 2 · SHARED

Team service

  • 2–5 projects on one VM or a small Kubernetes cluster
  • The service holds all tokens; users hold none
  • Triggered from the CLI, a Jira label, or a /sdlc fix MR comment

Move on when several teams want it and cost needs one owner.

STAGE 3 · PLATFORM

Managed service

  • Run by a platform or enablement team
  • SSO, access from GitLab group membership, a budget per project
  • Self-service onboarding, a skills catalog, a Slack bot and web UI for the gates

Track first-try verify rate, review rounds, cost per ticket, and revert rate.

Shared deployment

  • Control plane runs in its own namespace: API with SSO, orchestrator workers, a Redis queue, Postgres, the LiteLLM gateway, Langfuse, and a secrets manager.
  • Sandboxes run as Kubernetes Jobs in a separate namespace with gVisor, a NetworkPolicy that only allows the gateway, resource quotas, and a deadline. Each one is used for exactly one stage of one run.
  • Release with signed, versioned images and skill packs. Skill changes must pass the evals, and new versions go to the pilot project first.

Ownership

  • Platform team: pipeline code, images, core skills, org config, releases.
  • Guilds: the skill packs in the catalog, each with its own evals.
  • Project team: .sdlc/pipeline.yaml, repo skills and instructions, verify commands.
  • Human reviewers always merge AI-generated MRs. Bad outputs reported in the feedback channel become eval cases.
The full detail is in BUILD_AND_ROLLOUT.md and PLAN.md in the SDLC_workflow repo. Stage IDs match all three. Config keys and example values are a proposed design, so check the OpenSpec and Claude Code flags against the versions you pin.
